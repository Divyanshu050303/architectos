# Simulation engine

The simulation engine answers "what if" questions about an architecture revision: what if the
workload doubles, a component gets two more replicas, a database becomes unavailable, or a zone is
lost? It applies a **scenario** to an in-memory copy of the revision, the **overlay**. It then
evaluates the overlay next to the unchanged **baseline** with the existing Capacity, Reliability and
Cost Engines, and reports the differences.

**Simulation results are model-based projections.** They describe the architecture as declared,
evaluated by the engines' documented models. They do not guarantee real-world performance,
availability, cost or failure behavior. No telemetry is read and no production system is touched.
What the architecture, the request or a model does not state stays **unknown** or **unsupported**,
never zero, never assumed.

Code:
- `core/domain/simulations/`: the contract. It holds scenarios, the catalog, the overlay, results,
  comparison, limits, the port, the service and the queries.
- `engines/simulation/`: the orchestrator, validation, the context, the three evaluators, the
  registry and the port adapter.
- `persistence/`: migration 0018 and the repository.
- `apps/api/`: the routes and schemas (the HTTP contract is in [docs/api/simulations.md](../api/simulations.md)).

Decided in [ADR-017](../adr/ADR-017-deterministic-simulation.md).

## Purpose and scope

In scope:

- **Workload changes**: growth by a multiplier, compound growth over periods, a target rate or a
  target utilization. The Capacity Engine's own scenario applies them to the request's workload
  profile.
- **Configuration changes**: replicas, per-connection traffic, resilience settings, and resource or
  pricing settings of named nodes and connections. They are applied as Architecture IR edit
  commands to a copy of the revision.
- **Failures**: a component, a connection, or a declared zone or region becomes unavailable. The
  Reliability Engine's dependency and redundancy semantics judge the result.
- **Cost comparison**: the baseline and the scenario are priced with one organization pricing
  snapshot by the Cost Engine.
- **Comparing stored simulations**, but only where both ran on one common baseline with the same
  models and engine.

Out of scope, never approximated:

- Latency, queueing, error rates, retries and timelines.
- Where load goes after a failure.
- Failure probabilities, durations and outage predictions.
- Monte Carlo or any randomness.
- Live traffic replay, chaos experiments, provisioning, and changes to production or to the stored
  architecture.
- Telemetry ingestion.

Numerical results are never generated by a language model.

## Supported scenario types

The catalog (`core/domain/simulations/catalog.py`, served by `GET /simulation/catalog`) holds nine
versioned types. Each type declares its inputs and units, the elements it applies to, its overlay
semantics, the analyses it concerns, what they require, what it cannot express, and its limit.

| Type | Version | Applies to | Evaluated by |
|---|---|---|---|
| `workload` | 1 | the workload profile | capacity, cost (usage) |
| `replicas` | 1 | nodes: replica counts | capacity, reliability, cost |
| `traffic` | 1 | connections: routing shares and per-connection capacity (e.g. `traffic_ratio`) | capacity |
| `resilience` | 1 | nodes: availability, redundancy groups, failover, placement | reliability, cost |
| `resources` | 1 | nodes: throughput limits, per-request costs, storage and the pricing mapping | capacity, cost |
| `component_failure` | 1 | nodes, but not clients or boundaries | reliability |
| `connection_failure` | 1 | connections | reliability |
| `zone_failure` | 1 | a zone some component declares in `availability_zones` | reliability |
| `region_failure` | 1 | a region some component declares | reliability |

A configuration change's type follows from its property, with the precedence replicas, then
traffic, then resilience, then resources. Its analyses are the engines that read that property.
A property no simulated engine reads, such as a security or observability setting, is refused with
`not_simulated`, not silently ignored. The exact property lists per type are in the catalog.

## Scenario input contracts and units

A scenario (`core/domain/simulations/scenarios.py`) has a `name`, an optional `description`, and at
most one `workload` change, `changes` and `failures`. The rules:

- **Workload.** Exactly one of:
  - `growth`: a multiplier above 0;
  - `growth_rate` with `periods` (1 to 120): compound growth;
  - `target_rate`: a quantity with an explicit unit such as `requests/second`;
  - `target_utilization`: a ratio.

  The Capacity Engine's scenario rules validate it. Units are never guessed: `rps` is refused.
- **Changes.** Each change is `{element_id, property, value}`. The unit is part of the property name
  (`throughput_limit_per_second`, `storage_bytes`). The value is checked by the IR's own
  `PropertySpec` (type and range); `null` clears the property.
- **Failures.** Each failure is `{kind, target}`. The target must exist: a node (not a client or
  boundary), a connection, or a zone or region declared by some component.
- **Conflicts** are refused: the same property changed twice, a failure listed twice, or an element
  both changed and unavailable (`changed_and_unavailable`).

The request adds:
- `analyses` (default: every analysis the scenario concerns);
- `workload` (a capacity workload profile);
- `entries` (default: the clients);
- `pricing`: a snapshot id, `pricing_date` and `operating_hours_per_month`, validated by the Cost
  Engine's request rules;
- `assumptions`, which are recorded and never computed with;
- `label`.

Validation (`engines/simulation/validation.py`, `check_scenario`) is deterministic and runs before
anything is evaluated. Each error names the field, the reason and the element, for example
`{field: "scenario.changes.element_id", reason: "unknown_element", element_id: "ghost"}`.

## Overlay semantics and immutability

`apply_scenario` (`core/domain/simulations/overlay.py`) returns an **Overlay**:

- **Configuration changes** become IR edit commands, applied with `apply_commands` to a **copy** of
  the revision. This is all-or-nothing and re-validated against the IR's invariants: a change that
  breaks one, such as fewer replicas than the minimum healthy, is refused. Every changed value
  carries the provenance `user_input`, with reference `scenario:<fingerprint>` and actor
  `simulation`.
- **Failures** mark elements **unavailable**; nothing is removed, so what depended on them stays
  visible. A zone or region loss makes unavailable only the components whose declared placement
  lies entirely within it. Components that declare no placement are **undetermined**, never
  assumed safe.
- **Serialization**: `to_dict()` holds everything needed to explain and reconstruct the overlay
  (the baseline revision and its content hash, the scenario fingerprint, the overlay's content
  hash, each change as before → after, and the unavailable, undetermined and zone-lost elements).
  It never holds the architecture itself. `reconstruct()` rebuilds it from the stored revision and
  refuses (`not_reproducible`) if the hash differs.

The stored revision is never modified. Tests assert its serialization and content hash before and
after every fixture. The baseline revision and the overlay are always distinguished: the overlay
cites the baseline's number and hash, and has its own hash.

## Engine integrations

The orchestrator (`engines/simulation/engine.py`) runs these steps in order:

1. Check the limits.
2. Validate the scenario (`check_scenario` → a plan of parts, types and analyses).
3. Build the overlay and check the number of affected components.
4. Call each registered evaluator, in the fixed analysis order (capacity, reliability, cost), with
   the context, the overlay, the plan and the earlier evaluations.
5. Collect runs, deltas, entry impacts, component outcomes, unsupported items, trace and assumptions.
6. Canonicalize and bound the output.

The evaluators are:

- **Capacity** (`engines/simulation/capacity.py`) uses the Capacity Engine port once for both sides.
  The baseline is the workload profile. The scenario is a capacity `Scenario` carrying the
  multiplier and changes. It produces deltas for demand, capacity and utilization per resource, and
  system bottlenecks and highest utilization. It never adds a formula: scaling follows the engine's
  models, and a model with no stated linear scaling does not scale. Failures are reported as
  `failure_not_modeled`. Components the engine could not calculate under the scenario are listed as
  `capacity_<status>` with what is missing.
- **Reliability** (`engines/simulation/failure.py`) evaluates resilience changes with the
  Reliability Engine on both sides (path availability per entry). It judges failures with the
  engine's dependency closure, dependency roles, redundancy groups and failover modes:
  - **interrupted**: a required dependency is unavailable and nothing declared covers it;
  - **degraded**: only optional dependencies are unavailable;
  - **tolerated**: a declared redundancy group with automatic failover and enough healthy members;
  - **unknown**: failover mode or minimum healthy not declared, or placement undetermined, with what
    is missing;
  - **unaffected**.
- **Cost** (`engines/simulation/cost.py`) prices both sides with the Cost Engine and one snapshot.
  Usage comes from the simulation's own capacity run, shared through the context memo rather than
  run twice. The two sides are compared with the Cost Engine's own comparison. Deltas are the system
  `monthly_cost` (not comparable, `incomplete`, when a side's total is incomplete) and each changed
  line (`unknown_line` when a price is missing).

The registry holds one evaluator per analysis. Adding one needs no change to the orchestrator.

## Model versions and assumptions

- Every run records the analysis engine's **model set** (for example capacity's
  `replica-throughput` version) and the fingerprints of its baseline and scenario results. The
  baseline and the scenario are always evaluated in the same run, with the same model versions,
  snapshot and settings.
- The simulation records its **engine set**: the orchestrator `simulation` v1 and each evaluator v1.
  It also records the **scenario types** used, with their versions.
- Assumptions shown with each result include:
  - the workload multiplier;
  - the workload profile's own assumptions;
  - the cost estimate's basis (hours per month, snapshot, currency);
  - the request's assumptions, which are recorded and never computed with.
- Limitations are always `model_based` and `no_defaults`, plus `deltas_truncated` when the output
  limit applied.

## Execution limits

`SimulationLimits` (`core/domain/simulations/limits.py`) can be configured per engine instance,
within hard caps:

| Limit | Default and cap | When |
|---|---|---|
| `max_changes` | 50 | before anything is applied |
| `max_failures` | 50 | before anything is applied |
| `max_affected_components` | 1000 (the IR's node cap) | after failures are resolved, before any engine runs |
| `max_deltas` | 20000 | on output: cut in canonical order, stated as `deltas_truncated` |

An over-limit request is refused predictably: `422 invalid_simulation_request` with
`{field, reason: too_many | too_many_affected, limit}`, and nothing runs or is stored. Graph work is
bounded by the IR's size caps and the engines' own traversals. There are no loops over unbounded
inputs and no job system. Running is synchronous and rate-limited (120 per user per hour). The
largest architecture measured (the IR caps) takes about 2 s.

## Partial and unsupported results

A simulation's status is derived from what was established:

- **completed**: every requested analysis ran completely, every entry impact is known, and nothing
  is unsupported.
- **partial**: something ran, but a run is partial or unsupported, an impact is unknown, or some
  element could not be evaluated. Everything that was established is still reported.
- **unsupported**: no analysis could run. Each run gives its reason:
  - `not_concerned`: the scenario changes nothing that engine reads;
  - `no_workload`;
  - `no_pricing`;
  - `no_currency`;
  - `no_capacity_model` / `no_reliability_model` / `no_cost_model`;
  - `no_evaluator`.
- **failed**: an engine failed (`engine_error`, `invalid_output`). The failure is logged by its type
  only, and nothing partial is stored as if complete.

## Baseline comparison semantics

Each **delta** is `{analysis, element_id, metric, unit, baseline, scenario, difference, percentage,
comparable, note}`. The rules:

- Values are exact decimals, and `null` means unknown.
- `difference` is given only when both sides are known.
- `percentage` is given only when the baseline is not 0.
- A value that cannot be compared is marked `comparable: false` with a note. Examples: a total that
  is incomplete on one side, or a price that is missing.
- No cause is ever inferred: a delta states what changed, not why.
- Deltas are ordered by analysis, element and metric, and each difference cites its run's model set
  and fingerprints.

Comparing two stored simulations (`compare`) is done per analysis. An analysis is compared only
when both simulations ran it with the same engine version, the same model set and the same baseline
fingerprint (the same revision, request inputs and snapshot). Otherwise it is not comparable, with
the reason `not_run`, `different_engine`, `different_models` or `different_baseline`. Units that do
not match are never compared (`unit_mismatch`).

## Example scenario and result

A deterministic, supported scenario: double the workload of a web → api → db shop. `api` has 2
replicas at 60 requests/second each, and `db` has a total limit of 500 operations/second.

```json
{"scenario": {"name": "Double", "workload": {"growth": "2"}},
 "workload": {"name": "Peak", "type": "request_response", "peakRate": {"value": 100, "unit": "requests/second"}},
 "analyses": ["capacity"]}
```

Result (abridged): `status: completed`, one capacity run `completed`, summary
`deltas: {comparable: 8, not_comparable: 0, changed: 6}`, no score.

| Element | Metric | Unit | Baseline | Scenario | Difference | % |
|---|---|---|---|---|---|---|
| `api` | `work_rate.demand` | requests/second | 100 | 200 | 100 | 100 |
| `api` | `work_rate.capacity` | requests/second | 120 | 120 | 0 | 0 |
| `api` | `work_rate.utilization` | ratio | 0.833333333 | 1.666666667 | 0.833333334 | 100.00000012 |
| `db` | `work_rate.utilization` | ratio | 0.2 | 0.4 | 0.2 | 100 |
| `system` | `bottlenecks` | bottlenecks | 0 | 1 | 1 | — (baseline 0) |

The trace says why:
- `capacity.new_bottleneck.api.work_rate: exceeds_capacity`;
- `capacity.scaling.api.work_rate: 2 replicas -> 4 replicas (…, linear in replicas (stated))`, the
  replica model's own statement.

The assumption `capacity.workload_multiplier: 2` is listed. The same request always gives the same
`resultFingerprint`. These are projections from the declared throughputs, not a prediction of the
production system.

## Example: missing inputs

The same scenario **without a workload profile** is `unsupported`. The capacity run is
`{state: unsupported, reason: no_workload, message: "No workload profile was given: this analysis is
not calculated."}` and there are no deltas: nothing is estimated.

With a cache that declares no capacity and a third party, the result is **partial**. `unsupported`
lists `cache` and `stripe` as `capacity_insufficient_input`, with the missing properties (for
example `configuration.throughput_limit_per_second`). The `api` and `db` deltas are still reported,
and the cache's capacity is not given a value.

A component failure whose redundancy group declares no `failover_mode` gives the entry impact
`unknown`, with `missing: ["api-a.configuration.failover_mode", "api-b.configuration.failover_mode"]`.
The run is `partial`: automatic failover is never assumed.

## Example: an incompatible baseline cannot be compared

Two stored simulations with different workload profiles (100 and 500 requests/second) ran on
different baselines. `GET …/{first}/comparisons/{second}` returns the capacity analysis as
`{comparable: false, reason: "different_baseline"}` and **no deltas** for it. A second simulation
whose capacity run used another model version gives `different_models`, again with no deltas.
Values are never set side by side as if equivalent.

## Example: the architecture is unchanged

`db` fails in the shop above. The entry `web` is `interrupted`, `through: ["db"]`, with the
explanation "web requires db, unavailable with nothing declared to cover it." `api-a` and `api-b`
are `interrupted` and `db` is `unavailable`. The overlay's `unavailable_nodes` is `["db"]`. The
stored revision and its content hash are identical before and after: `GET` of the architecture
returns the same content, and the overlay cites that same hash as its baseline. A configuration
change such as `api.replicas: 2 -> 4` exists only in the overlay's `changes`, never in a revision.

## Adding a new scenario type safely

1. Add a `ScenarioType` to `core/domain/simulations/catalog.py`. Give it:
   - an id and version;
   - inputs with units;
   - `applies_to`;
   - the overlay semantics;
   - the analyses and what they require;
   - the unsupported conditions;
   - the limit.

   Configuration types must partition the simulated properties (a test enforces it).
2. If it needs a new kind of change, extend the scenario model with validation in the domain and
   reuse IR commands for the overlay. Never mutate the IR in place.
3. Map it to the engines that evaluate it in an evaluator. Reuse the engine's port and its own
   formulas: no duplicate formula in the simulation engine.
4. Keep unknowns unknown. Add an `Unsupported` item or a run reason instead of a default.
5. Add fixtures: a supported case, a missing-input case, determinism under reordering, and an
   unchanged revision. Map them in `tests/security/test_traceability_simulation_engine.py`.
6. Document the type here and in the API document. Bump its version when its semantics change:
   comparisons across versions are then refused.

A new analysis is a new evaluator with an `EvaluatorMeta` (analysis, version, requires ⊆
{workload, pricing}, unsupported), registered in `engines/simulation/registry.py`. The orchestrator
does not change.

## Known limitations

- Only what the engines model is simulated:
  - no latency, queueing, error rates, retries, timeouts or timelines;
  - no load redistribution after a failure;
  - no probabilities, durations or outage predictions.
- Failure impact follows declared dependencies, redundancy and failover only. An architecture that
  declares little gets `unknown` impacts and `partial` results.
- A zone or region failure affects only components that declare their placement. The others are
  undetermined.
- Cost is an estimate from the chosen snapshot, not an invoice: no currency conversion, no taxes,
  and no discounts the snapshot does not hold.
- Simulations run synchronously within the request, bounded by the limits. There is no background
  job system.
- The web app's proposed simulation contract (jobs, traffic presets, durations, timelines, error
  rates, impact levels) is not implemented. See the frontend contract.

## Persistence

Migration 0018 adds `simulations`, `simulation_components` and `simulation_deltas`. The design:

- The tables are **append-only**: triggers refuse updates, deletes and truncation.
- Rows are scoped to one project through same-project foreign keys to the architecture and the
  revision simulated.
- A simulation stores the request with its scenario snapshot, the requirements read, the provider
  and currency, the overlay, the engine set, the fingerprints, the summary, runs, entries,
  assumptions, trace, unsupported items and limitations.
- Components and deltas are stored as rows so they can be paged and filtered. The stored rows
  rebuild the result, whose fingerprint is checked again.
- Writes happen in one transaction under the project's share lock, with the audit entry
  `architecture.simulated`.

## Authorization

- Running needs `architecture.analyze` (members, admins and owners). Reading and comparing need
  `architecture.read` (viewers too).
- Every read is scoped by project and architecture. Outside the organization the answer is
  `404 project_not_found`, so existence is never revealed.
- Archived projects and architectures refuse new simulations. The check is made again under the
  lock after the calculation.
- Snapshots are read only from the project's organization.

## Determinism

The same revision, request, requirements, snapshot and settings give the same overlay, result and
`resultFingerprint`, even when the architecture's elements or the scenario's changes and failures
are given in another order. Everything is canonically ordered:
- components by node id;
- deltas by analysis, element and metric;
- runs by analysis;
- unsupported items by element and code.

Numbers are exact decimals. Identifiers come from content fingerprints or uuid5, and the only
random identifiers are the database row ids.

## Security of the engine itself

- The engine imports no network, database or randomness module, and executes no dynamic code.
- Engine failures are logged by the error's type only, never its message.
- Results never contain secrets: settings whose names look secret are not simulated properties, and
  the API returns only simulated values.
