# Evolution API

Deterministic architecture evolution analysis: how an architecture revision could evolve toward typed
goals, from the evidence the other engines stored for it. The engine proposes **candidates** —
configuration changes of existing elements, each generated by a versioned rule from current
evidence, validated on an overlay, evaluated by the engines that model each dimension, with its
trade-offs — and reports what it could not establish. The same revision, request, evidence,
requirements and policy always give the same candidates, findings and `resultFingerprint`.

**Candidates are proposals requiring engineering review and authorization.** Nothing is applied to
the architecture and no revision is created; the engine never ranks candidates, scores them or picks
one. Structural changes (new components, caches, queues, splitting a service, sharding, more regions)
are never proposed: they are reported as considerations for human review, because no model here
evaluates them. Missing evidence stays missing: it is requested, never treated as a benefit.

On every project endpoint: `404 project_not_found` / `architecture_not_found` outside your
organizations (existence is never revealed) and `403 permission_denied` without the permission.
Viewers read analyses; members, admins and owners also run them.

## Running an analysis

Synchronous: analyzed and stored in the request, append-only. Rate limit: 60 per user per hour.
Archived projects and architectures refuse new analyses (`409`). A refused request stores nothing.

```json
{
  "goals": [
    {"type": "increase_workload", "target": {"value": 200, "unit": "requests/second"}},
    {"type": "availability_objective", "target": {"value": "99.9", "unit": "%"}},
    {"type": "address_finding", "finding": {"source": "security", "findingId": "sec_…"}}
  ],
  "constraints": {"frozenElements": ["db"], "excludedCategories": [], "maxReplicas": 8},
  "evidence": [{"source": "capacity", "analysisId": "01a0de60-a784-7244-8ecc-62afb5352f47"}],
  "assumptions": [{"key": "peak", "statement": "Peak lasts two hours."}],
  "label": "Next quarter"
}
```

- `goals` (1 to 20), each typed with an explicit target and unit — never inferred from a benchmark:
  `increase_workload` (a rate), `cost_ceiling` (`amount` and `currency`, per month),
  `availability_objective` (a ratio or %), `recovery_objective` (a duration), `address_finding`
  (`finding`: `reliability`, `security`, `observability` or `validation`, and the finding's stable
  id), `observability_coverage` (`dimension`), `satisfy_requirement` (`requirementId`, in force).
  Fields a type does not use must be absent. Operational complexity, new functional requirements and
  migrations are not goals the engines evaluate.
- `evidence`: for each engine, the stored analysis to use (it must be of this architecture); default
  the latest usable one. Only analyses of the revision's exact content (same content hash) count;
  others are reported `stale` and never used.
- `constraints`: elements no candidate may change, categories to exclude, a replica ceiling. A
  candidate a constraint excludes is reported (`excluded_by_constraint`), not silently dropped.
- `requirementIds`: the requirements read (default all in force); `scope`: the nodes considered.
- `assumptions` are recorded with the analysis, never computed with.

Refusals are `422 invalid_evolution_request` with `details: {field, reason}`, for example
`goals.target` / `wrong_dimension`, `goals.amount` / `not_applicable`, `goals` / `duplicate`,
`requirement_ids` / `unknown_requirement`, `evidence.analysis_id` / `unknown_analysis`.

## The analysis

`status`: `completed` (every goal evaluated on current evidence), `partial` (some evidence stale or
missing, or a goal not evaluable), `insufficient_evidence` (no goal could be evaluated), or `failed`
(`error.code` `engine_error`).

- `findings[]`: `{id, type, message, goal, elementIds, evidence, missing}`. Types: `stale_evidence`,
  `missing_evidence`, `goal_unsupported`, `goal_not_evaluable`, `goal_already_met`,
  `no_applicable_rule` (with the engine's own recommendation), `structural_consideration` (for human
  review), `excluded_by_constraint`. `missing` names what would let the engine decide.
- `evidence[]`: every stored analysis considered, with its `state` (`current`, `stale`, `missing`),
  revision number, content hash and model version.
- `summary`: counts only (goals, candidates by category and by goal, findings by type, evidence by
  state) — no score. `limitations`: `proposals_only`, `configuration_only`, `model_based`, and
  `candidates_truncated` / `findings_truncated` when a limit applied: at most 25 candidates are
  validated and evaluated per analysis (the first in canonical order; narrow the scope or the goals
  to see others) and 1000 findings are kept; a finding lists at most 200 elements ("… and N more").
- `inputs`: the request as stored, the requirements read, the policy, provider and currency, and the
  stored analyses whose inputs were reused for impacts (`impactInputs`).

## Candidates

`GET …/candidates?category=&validation=&goal=&cursor=&limit=`, in canonical order (category, then
id) — **not a ranking**. Each candidate:

- `id` (stable: from the rule, the baseline and the changes), `status` (always `proposed`), `rule`
  (`id`, `version`), `baseline` (architecture, revision number, content hash), `category`
  (`scaling`, `redundancy`, `security_control`, `instrumentation`), `changes` (`elementId`,
  `property`, `value`), `goals`, `rationale`, `evidence` (current only);
- `benefits`, `tradeoffs`, `complexity`, `migration`, `risks`: `{dimension, code, statement, basis,
  evidence}` — `basis` is `modeled` (an engine's model), `rule` (the rule's documented reasoning) or
  `consideration` (for human review);
- `validation`: `valid` (under the modeled constraints only — not production readiness),
  `invalid`, `not_evaluable`, `unsupported`, with `validationNotes` (findings the candidate
  introduces or resolves, requirements it would violate, with the exact elements);
- `impacts`: per dimension `{dimension, state, source, reason, baselineFingerprint,
  candidateFingerprint, modelVersion, inputs, deltas, changes, assumptions, missing}` — from the
  Simulation Engine (capacity, reliability, cost) or the Security and Observability engines; a
  dimension an engine could not establish stays `unsupported` with its reason;
- `consequences`: the trade-off table, one row per dimension, `{dimension, direction, basis,
  statement, evidence}` with `direction` `improves`, `worsens`, `mixed`, `unchanged`, `unknown`,
  `not_evaluated` or `consideration`.

`GET …/candidates/{candidateId}` adds `overlay`: the candidate re-applied to its exact baseline in
memory — each change `before -> after`, the IR's structural diff and the overlay's content hash;
`null` when the candidate cannot be applied (its validation says why). Never applied to the
architecture.

`GET …/alternatives`: for each goal, the candidates that address it and each one's direction per
dimension, side by side. Nothing is chosen.

## Catalog

`GET /evolution/catalog`: the goal types, the candidate categories, each rule's contract (triggers,
goals, required evidence, the properties it may change, preconditions, benefits, trade-offs,
unsupported conditions, validation, analyses, version) and the limits. The rules: `scale-replicas`,
`scale-cpu`, `add-replica`, `require-tls`, `encrypt-at-rest`, `enable-signal`.

## Audit

`architecture.evolution_analyzed` (analysis id, revision, status, goal, candidate and finding
counts), in `GET /organizations/{orgId}/audit-log`. Decisions drafted from an analysis are
[decision records](decisions.md).
